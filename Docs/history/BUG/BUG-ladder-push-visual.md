## Report and approved behavior

Holding F at a raised ladder top previously left its visual motionless for the entire push, followed by an instant snap to the ground. The user first requested visible motion like raising, then reported the instantaneous return pose on cancellation and explicitly approved immediate implementation of balance-point behavior for both raising and pushing. Subsequently the user reported occupants still climbing the original stationary route, and approved pausing traversal, following the tilted ladder, resuming after return and falling at the outward balance point. These changes expand the existing claimed task on its current branch.

- `SiegeLadderState` retains progress on cancellation and gradually settles back to the starting endpoint before balance. Once balance is reached, motion commits and continues without a raiser/pusher, even if the pusher becomes blocked. A return already underway finishes before a fresh attempt can start.
- `SiegeLadder.HasWall` derives the balance fraction from the actual base-to-edge rotation: vertical angle (90 degrees) / full raised angle. It is not a fixed 50% input threshold. `PlaceholderLadderView` uses the same logical direction and `RaisedFraction`, with the existing cosmetic lift applied to the whole pose. The existing 3s raise / 2s push times set both controlled and automatic rotation rates; this is deterministic angle motion, not a rigidbody gravity simulation.
- `IsSettling` rejects new raise/entry requests. `CanBoard` also prevents entry during controlled pushing. Existing FIFO requests are retained; friendly use continues to prevent starting a push. A short F gesture must begin and end on a boardable ladder, so a gesture started during settling cannot become boarding when released just after completion. Contextual hints indicate automatic motion.
- `CurrentDirection` / `FollowTilt` share one logical pose between the placeholder visual and occupants. `SiegeAttackerBrain` and `LadderTraveller` pause traversal progress during pushes/return, moving the ladder contact point with the tilt while retaining the body/approach offset in world space. Once the return completes, traversal resumes. The character placeholder remains upright; no hanging character animation was added.
- `ClimberDislodged` releases the occupant and starts its existing fall controller at the outward vertical balance point. This event exposes the exact balance pose even if a long tick crosses it; the later `Toppled` event finishes the ladder motion without dropping the same occupant twice. Falling starts at the actual hanging height, so a low occupant may take no damage under the existing safe-height rule. Raising cancellation does not count as toppling. Support destruction, disabling and battle reset still force immediate collapse/reset. No shared combat-core or serialized asset edits were required.

## Low-height ground penetration follow-up

The user subsequently reported an enemy disappearing into the ground. `SharedLadder_LowEnemyPush_StaysAboveGroundAndLands` reproduced this with a real enemy boarding at 70% of the use radius and immediately being pushed: its foot moved to **y = -0.34763819**, below the ground. The previous mid-height regression did not cover this case.

Root cause: boarding starts within a radius, so the original raised position includes an approach offset away from the ladder foot. Fully rotating that offset around the foot can put a low occupant below ground before the balance point; a downward-only ground ray then cannot see the ground above it. `FollowTilt` now projects the contact distance onto the raised ladder axis (nonnegative), applies only that contact point's displacement, and retains the body/approach offset in world space. This removes the downward rotation of the offset instead of changing the shared fall controller or teleporting an already sunken unit. Balance-point separation still prevents characters from staying attached to the downward-facing ladder all the way to the ground.

The first regression run failed at the below-ground assertion as expected. After the fix, that assertion passed; a later assertion in the same test then exposed a test sequence that attempted to restart a push during the deliberately locked return motion. The test now waits for return to finish before starting the second push. Final verification: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File Tools/Agent/unity-verify.ps1 -Mode all -Filter Siege` passed dotnet precheck and Unity compile, EditMode **20/20** (4.07s) and PlayMode **25/25** (14.3s). This includes the low-height reproducer, mid-height attachment/resume/fall and existing siege regressions. The intermediate failures described above are resolved. Physical-key review and standalone build remain unverified.
